# Unified MoM+YoY breakdown table and mobile-responsive filter for digital channel pages

Three digital channel pages (branchless, QRIS merchant, VA) receive the same structural overhaul: the previously separate MoM breakdown table and YoY chart+table are merged into a single unified table that calls both endpoints in parallel and joins by cabang kode. A collapsible filter toggle improves mobile usability. Template literals are replaced with string concatenation throughout, and each page gets a distinct color theme (emerald, purple, blue).

**Watch for:** Silent partial-data rendering when one of two parallel fetches fails (confirmed). Nearly identical ~120-line `fetchUnifiedBreakdown` function duplicated across three files with no shared abstraction (confirmed). Map merge key mismatch between MoM data (cabang `kode`) and YoY data (cabang `kode`) when one endpoint returns data the other doesn't—rows appear with zeroes in one half of the table with no visual indication that data is incomplete (likely).

## High-level view

The core design decision is merging two API responses client-side via a `Map` keyed on `cabang.kode`. For KONSOLIDASI this drills into the nested `korwil > cabang` arrays of both responses to extract all 28 branches; for KORWIL it takes only that korwil's cabang array; for a specific branch it falls back to `kode || nama` as the merge key. The approach eliminates a dedicated YoY chart (and its ApexCharts instance) in favor of a flat table, reducing render complexity and DOM size at the cost of losing the visual bar comparison.

The mobile-responsive changes add a `toggleFilter()` function that hides the filter form on small screens by default and reveals it on tap. This is implemented identically in all three pages—same element IDs, same class toggling logic—making the pages completely self-contained but tripling any future maintenance burden.

The template-literal-to-concatenation migration touches every dynamic HTML string. It has no behavioral effect but makes the HTML-building lines substantially longer and harder to read, which raises the difficulty of spotting injection paths during future audits.

<summary>Issues (5)</summary>

1. **Partial fetch treated as success** — If `resMom` succeeds but `resYoy` fails (network timeout, 500), the catch block is not reached because `Promise.all` only rejects if one promise rejects at the fetch level, not at the HTTP-status level. The code checks `jYoy.status === 200` before merging YoY data but shows zero-filled YoY columns without any indicator that data is incomplete. Add a visual warning when one half returns non-200.
2. **Grand total uses MoM `growth_nom` vs YoY `yoy_growth_nom`** — The field name for MoM growth is `growth_nom` while YoY uses `yoy_growth_nom`. If the API ever changes the MoM field name to match YoY naming, the grand total MoM growth column will silently display zero. This inconsistency is inherited from the API but worth documenting.
3. **100+ lines duplicated across three files** — `fetchUnifiedBreakdown`, `toggleFilter`, `parseAreaValue`, and the merge logic are copy-pasted with only color-class and channel-name differences. Extract a shared JS module or PHP include to reduce maintenance surface.
4. **XSS via unsanitized API response** — `row.nama`, `t.label`, and other API-returned strings are injected directly into `innerHTML` without escaping. If a branch name ever contains `<script>` or HTML entities, it will be rendered as markup. This applies to all three pages.
5. **Filter hidden on mobile initial load hides date defaults** — The filter is hidden (`class="hidden md:block"`) so on mobile the auto-populated dates are invisible until the user taps "Tampilkan Filter". Data loads immediately on page init using those hidden defaults, which could confuse users who don't realize what period they're looking at. Consider showing the active period label more prominently or auto-expanding the filter on first load.

## Parallel fetch and client-side merge via Map

The `fetchUnifiedBreakdown` function fires two `fetch` calls in parallel—`detail_breakdown_transaksi` for MoM and `yoy_transaksi` for YoY—then merges results into a single `Map<kode, row>`. The MoM pass populates the map first; the YoY pass enriches existing entries or inserts new ones with zeroed MoM fields.

The merge key for KONSOLIDASI and KORWIL modes is `cb.kode` (a string like `"001"`). For specific-cabang mode it falls back to `kk.kode || kk.nama`, which means if an entry has no `kode` property the branch name becomes the merge key. If the YoY endpoint returns the same branch with a slightly different `nama` string (e.g., trailing space, different casing), the merge will create a duplicate row—one with MoM data only, one with YoY data only. This is a **likely** edge case if the two endpoints pull from different database views.

A more defensive approach would normalize keys (`trim().toUpperCase()`) before insertion, or use a composite key of `kode + nama`.

## Partial-failure rendering without user feedback

```js
const [resMom, resYoy] = await Promise.all([...]);
const jMom = await resMom.json();
const jYoy = await resYoy.json();
```

If either response returns malformed JSON, `.json()` throws and the catch block renders "Gagal memuat data." But if one endpoint returns `{ status: 500, data: null }`, the code silently proceeds: the guard `if (jYoy.status === 200 && jYoy.data && jYoy.data.data)` skips enrichment, and the table renders with zero-filled YoY columns and a zero grand total for YoY. There's no visual signal that half the data is missing. A user seeing `0` in the YoY column for every branch could mistake it for actual zero-growth rather than missing data. (confirmed—traceable in the code)

## HTML injection surface in innerHTML concatenation

Every data row is built via string concatenation directly into `innerHTML`:

```js
tbody.innerHTML += '<tr>...' + row.nama + '...</tr>';
```

`row.nama` comes from an API response that ultimately reads from a database. If a branch name contains `<img onerror=...>` or even an accidental `&` or `<`, the page will render broken HTML or execute scripts. All three pages share this pattern. Since this is an internal dashboard the risk is lower, but a stored-XSS via branch-name manipulation remains possible if the data pipeline doesn't sanitize at write time. (confirmed—no escaping present in any of the three files)

## Code duplication across pages

The three files differ only in:
- Color class names (`emerald` vs `purple` vs `blue`)
- `CHANNEL` constant (`'BRANCHLESS'` / `'QRIS'` / `'VA'`)
- Summary card filter keyword (`.includes('BRANCHLESS')` vs `'QRIS'`)
- VA page retains a Mandiri-vs-Permata monthly table above the unified breakdown

Everything else—`toggleFilter`, `fetchUnifiedBreakdown`, `parseAreaValue`, `initPage`, `loadCabangList`, the entire merge logic—is identical. This is approximately 120 lines of duplicated logic per page. Any bug fix or feature change (e.g., adding a "data incomplete" banner) must be applied three times.

## YoY chart removal trade-off

The old pages had an ApexCharts bar chart comparing current-year vs prior-year nominal per korwil. This is now gone entirely—replaced by percentage badges in the table. The bar chart provided at-a-glance magnitude comparison (seeing that one korwil's bar is 3x another's), which percentage badges don't convey. Whether this is a regression depends on how stakeholders used the chart; flagging it because the change removes a visualization without replacing it with another.
