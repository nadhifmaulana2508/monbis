# Migrasi Bucket: konsolidasi detail, run off formula fix, and summary breakdown

This change makes three corrections to the migrasi_bucket page. First, the detail modal (showing individual loan accounts) now works in konsolidasi mode (all branches), where previously it was gated by a frontend `gIsKonsol` check and backend 400-response guards. Second, the "Run Off" calculation per row is replaced: the old formula (`max(0, os_m1 - sumNonO)`) gives way to a backend-computed value of `angsuran_pokok + lunas_os_m1`, fetched from `transaksi_kredit`. Third, a new summary panel renders Pemburukan/Stay/Perbaikan counts broken down by SC/FE/BE bucket category. Client-side pagination (20 items/page) is added to the detail modal to keep large result sets manageable.

**Watch for:** The run off fallback in the frontend uses `||` which treats a legitimate zero run off as falsy, silently reverting to the old formula (confirmed). The LPAD-based exclusion filter for konsolidasi queries (`<> '000'`) wraps the column in a function, preventing index usage on `kode_cabang` for what could be full-table scans across all branches (likely).

## High-level view

The konsolidasi unblock removes the frontend gate and switches the backend from rejecting null `kode_kantor` to building a conditional SQL fragment that either filters on a specific branch or excludes the synthetic '000' branch. The REALISASI detail path is deliberately left gated since it requires a specific branch.

The run off formula fix adds a new loop over the M-1 account set in `migrasiBucketOsc`, calling the existing `fetchAngsuranMap` to pull angsuran_pokok from `transaksi_kredit`, then sums that with the OS M-1 of lunas accounts per from-bucket. The frontend consumes `run_off_per_from` from the response, but the fallback expression `getNum(runOffData[f]) || Math.max(...)` treats zero as falsy, so any bucket with genuinely zero run off will fall through to the old (incorrect) formula.

The summary breakdown iterates the same M-1 account set, classifying each account's migration direction against `$tagMap` to populate a three-tier (SC/FE/BE) structure with noa/os counts for pemburukan, stay, and perbaikan.

Pagination is client-side: all detail rows are fetched in one request, held in `currentFilteredList`, and sliced by `PAGE_SIZE=20` for rendering. Sorting and filtering reset to page 1 and re-slice the in-memory list.

## Run off fallback treats zero as missing

In `pages/migrasi_bucket.php` around line 453:

```javascript
const runoff = getNum(runOffData[f]) || Math.max(0, os_m1 - sumNonO);
```

JavaScript's `||` operator falls through when the left side is any falsy value, including `0`. If `runOffData[f]` is legitimately `0` (a bucket where no angsuran was paid and no accounts became lunas), the frontend falls back to the old incorrect formula. The fix:

```javascript
const runoff = (runOffData[f] !== undefined && runOffData[f] !== null)
  ? getNum(runOffData[f])
  : Math.max(0, os_m1 - sumNonO);
```

Confirmed: `getNum(0)` returns `0`, and `0 || anything` evaluates to `anything`.

## LPAD filter prevents index usage in konsolidasi detail queries

Both `getMigrasiBucketDetailActual` and `getMigrasiBucketDetailOLunas` use this pattern when `$kc` is null:

```php
$kcFilter_h = " AND LPAD(CAST(h.kode_cabang AS CHAR),3,'0') <> '000' ";
```

Wrapping `kode_cabang` in `LPAD(CAST(...))` forces a full scan of any index on that column. If `kode_cabang` is stored as `CHAR(3)` or `VARCHAR`, a direct `<> '000'` comparison would preserve index eligibility. If numeric, `<> 0` works. The `fetchAngsuranMap` method already uses the same `LPAD` pattern (project-wide convention), but it becomes more impactful on detail queries that return per-account rows rather than aggregates.

## Large unpaginated backend responses for konsolidasi detail

In konsolidasi mode (all branches), a single from/to bucket pair could contain thousands of accounts returned in one JSON response. The frontend holds the full array in `currentDetailData` and paginates client-side — this works for moderate sizes but may stress browser memory and network transfer for large portfolios. Server-side pagination with LIMIT/OFFSET would cap the response size, at the cost of losing client-side sort/filter on the full dataset.

## Summary classification assumes absent-from-CUR means lunas

The summary loop defaults accounts missing from `$CUR['bucketByAcc']` to bucket 'O':

```php
$to = $CUR['bucketByAcc'][$acc] ?? 'O';
```

This conflates "not present in the current snapshot" with "paid off". If the current snapshot is incomplete (data ingestion delay, excluded records), these accounts are counted as perbaikan. The same pattern exists in the matrix-building loop — consistent with existing behavior, but the summary makes the effect more visible by aggregating direction counts. Worth verifying that snapshot completeness is guaranteed before this function runs.

## Duplicated column definitions in pagination

The column definitions array is duplicated between `renderDetailTable`, `MB_goPage`, and the sorting closure. If a column is added or reordered, all three must be updated in sync — a maintenance hazard as the table evolves.
